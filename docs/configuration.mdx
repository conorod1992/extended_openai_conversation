Connection details and conversation-agent behaviour are configured in separate places so there is one clear editor for each responsibility.

## Access Configuration

<Steps>
  <Step title="Configure the provider connection">
    Go to **Settings** > **Devices & services** and add or reconfigure Extended OpenAI. The native Home Assistant flow contains API provider, key, base URL, API version, organisation, and authentication/bootstrap settings.
  </Step>
  <Step title="Open the agent editor">
    Choose **Extended OpenAI** in the Home Assistant sidebar, select a conversation agent, then open **Configuration**.
  </Step>
  <Step title="Manage Function Tools">
    Use **Capabilities → Functions** to browse configured tools and optional Function Groups. **Edit** opens the large YAML-first function editor; **Create group** opens friendly group fields and a searchable function checklist. Each item saves directly.
  </Step>
</Steps>

The frontend edits the existing Home Assistant conversation subentry through authenticated WebSocket commands. It does not create a separate configuration store. Configuration is one full-width settings document with lightweight jump links, search, and responsive fields inside each section. Settings edits remain local until **Save configuration** is pressed; the Save/Revert bar appears only while changes exist. Function and Function Group operations save directly without saving or discarding unrelated settings. Model-specific fields are supplied by the backend. Simple dependent settings remain visible but disabled so available options are discoverable and the layout stays stable.

The **Prompt & context** section gives new agents two simple default-on controls for Home Assistant-local date/time and exposed-device names/states. Generated blocks are volatile integration context after the intact user prompt. Optional advanced formatting templates stay collapsed and clearing an override restores the maintained default. Existing agents keep their prompt byte-for-byte and migrate with generated date/device blocks off, avoiding duplicated legacy Jinja.

**Preview effective request** uses the production builders to show fresh-request system/context, effective custom Function Tools, the initial Function Group loader/catalogue, integration/provider-hosted tools, and non-secret request settings. It excludes user input, conversation/tool-call history, query-derived persistent memories, credentials, and opaque provider content, and has no save/provider/usage/memory/group/history side effects. Counts are exact for displayed text or canonical local JSON; Function Group savings include loader overhead and compare against eagerly sending every enabled custom schema. Real provider token and cache reporting remains authoritative.

To improve natural provider prompt-cache reuse, the rendered user-authored prompt remains one indivisible block. Stable integration-owned memory, temporary-memory, Knowledge, archive, and continuation guidance follows where enabled; volatile retrieved persistent-memory and active temporary-memory data is placed later. Tool schemas remain tool definitions, request message roles are unchanged, and actual cache hits remain provider-controlled.

Function Tools use YAML as the only editor format. Existing tools are serialized by the Python backend as readable single-tool YAML (`spec:` plus `function:`), and new tools begin with a generic template. **Validate** parses YAML and applies the same backend function schemas used at runtime without executing the function. Validated name, type, and description become the metadata shown in the list; they are not separate sources of truth.

The Add Function Tool dialog also offers **Insert Built-in Function**. Built-in functions are implemented directly by Extended OpenAI Conversation; the picker inserts a complete editable native preset into the existing YAML editor without saving it. Already-configured implementations remain visible and are labelled accordingly.

Function Tools are enabled by default. The card switch persists immediately; top-level `enabled: false` in saved YAML likewise retains a tool and its Function Group membership without sending its schema to the model or allowing it to execute. Administrators can persist the same state through `extended_openai_conversation_responses.enable_function_tools` and `extended_openai_conversation_responses.disable_function_tools`. These Home Assistant actions are deliberately not exposed as model-facing tools unless an advanced user explicitly wraps them.

Function Groups are separate metadata around those unchanged tools. Existing ungrouped functions remain **Always available**. Choose **Load when needed** to send only a compact group catalogue until the model requests the group in the normal tool loop. Loaded groups persist for the active conversation, may add one provider round-trip on first use, and require no classifier/router model or keyword matching. Deleting a group moves its functions back to **Always available** without deleting them. See [Function Groups](/features/function-groups).

## Agent lifecycle and portability

- **Duplicate** creates a new conversation subentry with a `- Copy` title and validated configuration. It does not duplicate memories, archive sessions, Knowledge sources, or usage history.
- **Export** downloads a human-readable, versioned JSON document containing agent-level behaviour only. It is disabled while the settings draft is dirty. Entry-level API credentials and retained runtime data are excluded, and common credential fields receive best-effort redaction. Function Tool definitions can still contain sensitive values in arbitrary strings, URLs, templates, commands, headers, or provider-specific fields, so review exported files before sharing them.
- **Import** validates and previews a versioned JSON/YAML document before it can create a new agent or overwrite the current agent. Creating a new agent preserves the current draft. Current-agent overwrite requires confirmation, explicitly discards a dirty draft, and never changes provider credentials.

## Full Backup & Restore

**Export configuration** remains the lightweight format for reusing or sharing agent behaviour. The separate **Backup & Restore** section creates a private recovery or migration backup for one conversation agent. It includes normalized saved configuration, persistent memories, active temporary memories with their original absolute expiry, canonical Knowledge source content and metadata, retained archive sessions and turns, and complete persisted usage totals, daily aggregates, requests, and runs.

Provider credentials, API keys, OAuth tokens, parent config-entry secrets, active requests or conversations, currently loaded on-demand Function Groups, locks, caches, and derived indexes are not included. A migrated agent may therefore require its provider connection to be reconfigured separately.

Selecting a backup only validates it and opens a human-readable summary. No state changes until **Restore everything** is explicitly selected. Restore uses deterministic replacement semantics rather than merging: current configuration and each backed-up storage category are replaced, usage is not added or double-counted, expired temporary memories are dropped, unexpired ones retain their original expiry, and the Knowledge search index is rebuilt from source content. A failed storage commit triggers a best-effort rollback to the pre-restore snapshot. Because full backups can contain prompts and private user-owned data, store the JSON file securely.

## Speech / TTS post-processing

Enable speech post-processing under **Configuration → Spoken response** to clean both progressive and completed TTS. Built-in cleanup uses a bounded, stateful stream parser, so links and URLs split across provider deltas are removed before Home Assistant feeds them to TTS. The original response remains in ChatLog history, events, archive, memory/context, and diagnostics. Home Assistant exposes one shared progressive listener for visual updates and TTS, so live visual deltas are cleaned too; retained content remains original.

The processing order is:

1. built-in Markdown/link cleanup
2. ordered custom regex replacements
3. final whitespace cleanup
4. trimming before TTS

Built-in options can remove Markdown links/citations, bare URLs, and conservative formatting markers such as headings, emphasis, inline-code markers, and list bullets. Responses API structured URL annotations are retained with native response items, while a provider-neutral text fallback protects Responses, Chat Completions, and compatible-provider streams. Use **Preview spoken text** to run sample text through the deterministic completed-response pipeline.

Custom replacements use standard Python regular expressions and affect spoken output only:

```yaml
- pattern: '\[[0-9]+\]'
  replacement: ''
- pattern: '\bHA\b'
  replacement: 'Home Assistant'
```

Regex is an advanced feature. Rules run sequentially on the completed response, are length/count limited, and invalid patterns are rejected during validation. Because an arbitrary regex can depend on future text, progressive TTS is disabled for an agent whenever custom rules are configured. Unexpected persisted runtime failures are logged and skipped so they cannot break conversation processing.

## Configuration Options

### Options

<AccordionGroup>
  <Accordion title="Prompt">
    **Type**: Template (Jinja2)

    **Default**: Behavioural system instructions; live date/device context is managed separately

    Custom system prompt to guide AI behavior. Supports Jinja2 templates with access to context variables and custom functions.

    ### Available Variables

    **Context Variables:**
    - `ha_name` - Home Assistant location name
    - `exposed_entities` - List of exposed entity objects
    - `current_device_id` - Device ID where conversation was initiated
    - `user_input` - User input object with conversation context
    - `skills` - List of enabled skill objects

    **Extended OpenAI Functions:**
    - `{{extended_openai.exposed_entities()}}` - Get list of exposed entities
    - `{{extended_openai.working_directory()}}` - Get working directory path
    - `{{extended_openai.skill_dir(name)}}` - Get skill directory path by name

    **Home Assistant Template Functions:**
    - `{{now()}}` - Current datetime
    - `{{area_id(entity_id)}}` - Get area ID for entity
    - `{{states}}` - Access all entity states
    - And all other [Home Assistant template functions](https://www.home-assistant.io/docs/configuration/templating/)

    ### Example Usage

    ```jinja
    You are a helpful assistant for {{ha_name}}.
    Current area: {{area_id(current_device_id)}}
    Working directory: {{extended_openai.working_directory()}}

    {% if skills %}
    Enabled skills: {% for skill in skills %}{{skill.name}}{% if not loop.last %}, {% endif %}{% endfor %}
    {% endif %}
    ```

    Date/time and exposed devices normally come from the first-class context controls. The variables and functions remain available for advanced custom prompts and formatting overrides.
  </Accordion>

  <Accordion title="Model">
    **Type**: String

    **Default**: `gpt-5-mini`

    Select the OpenAI model to use. Examples:
    - `gpt-5-mini` - Fast and cost-effective
    - `gpt-4o-mini` - Balanced performance
    - Custom models from compatible providers
  </Accordion>

  <Accordion title="API mode">
    **Type**: Select

    **Default**: `Auto`

    Choose the OpenAI endpoint used for this agent:

    - `Auto`: Use the Responses API for GPT-5.6 and later GPT-5 models. Use Chat Completions for older models.
    - `Chat Completions`: Always use `/v1/chat/completions`.
    - `Responses`: Always use `/v1/responses`.

    <Note>
    Use `Responses` when a custom model or compatible provider supports the Responses API but its model name does not match the automatic GPT-5.6 detection. Use `Chat Completions` if a compatible provider does not implement `/v1/responses`.
    </Note>
  </Accordion>

  <Accordion title="Continue conversation">
    **Type**: Select

    **Default**: `HA Default`

    Control whether an Assist voice device listens for another utterance after it speaks a successful response:

    - `HA Default`: Do not override Home Assistant. Home Assistant currently derives continuation from whether the final assistant text ends in a recognized question mark.
    - `Always`: Explicitly request another utterance after every successful response. Error responses do not continue.
    - `Conditional`: Let the language model decide independently for each final response.

    Conditional mode adds an internal structured finalizer tool to the existing model turn. The tool carries both the complete spoken response and a boolean `continue_conversation` decision. The integration consumes the boolean as control metadata and exposes only the response text to Home Assistant. Normal Home Assistant tools still run first, and no second model request is made solely to classify continuation.

    The model is instructed to continue for direct questions, clarification, choices, and intentionally multi-turn interactions. It is instructed to stop after completed commands, final answers, and status reports.

    <Note>
    Home Assistant stores the request in `ConversationResult.continue_conversation`. The Assist pipeline forwards it and routes the next utterance back to the agent that requested continuation. Current ESPHome Assist satellites restart the microphone after TTS without requiring a wake word. Text clients may ignore the flag. Older or custom satellite clients must support it themselves, and device timeouts, firmware, VAD, or a user stop can still end listening.
    </Note>
  </Accordion>

  <Accordion title="Max Tokens">
    **Type**: Integer

    **Default**: `500`

    Maximum number of tokens in the AI response. Controls response length and API costs.

    <Note>
    Chat Completions uses `max_tokens` or `max_completion_tokens`, depending on the model. Responses uses `max_output_tokens`.
    </Note>
  </Accordion>

  <Accordion title="Memory mode">
    **Default**: Off

    - `Off`: Disable persistent memory.
    - `Manual`: Store memories only after an explicit remember request. Relevant memories can still be retrieved automatically.
    - `Automatic`: Allow proactive storage of stable, useful facts under the existing memory safety rules.

    **Automatically include memories** selects `0–10` records once from the opening message and reuses them for that conversation; `0` is tool-only. Lightweight lexical retrieval is local and default. Hybrid semantic retrieval uses embeddings only and falls back to lexical if the provider or model does not support them. Use **Extended OpenAI → Memories** to inspect, filter, add, edit, delete, or clear permitted personal and shared scopes. See [Persistent memory](/persistent-memory) for keys, importance, freshness, upserts, storage, and privacy.
  </Accordion>

  <Accordion title="Knowledge Library">
    **Default**: Off

    Enables read-only, on-demand access to maintained per-agent Knowledge sources. Use **Configure > Manage knowledge** or the **Knowledge Library** sidebar panel to create, edit, filter, and delete sources. Stored sources are retained while the option is Off.

    When enabled and populated, the integration adds `knowledge_search`, `knowledge_list`, and `knowledge_get` automatically in both API modes. Full source contents are not added to each prompt, and the model cannot modify the library. See [Knowledge Library](/features/knowledge-library).
  </Accordion>

  <Accordion title="Maximum Function Calls Per Conversation">
    **Type**: Integer

    **Default**: `10`

    Limit the number of function calls in a single conversation to prevent infinite loops.

    <Warning>
    Without this limit, functions might call each other repeatedly, consuming API credits.
    </Warning>

    **Recommended value**: `5-10`
  </Accordion>

  <Accordion title="Skills">
    **Type**: Multi-select

    Select which skills to enable for this assistant. Skills provide reusable AI capabilities and instructions.

    <Info>
    Skills are loaded from `/config/extended_openai_conversation_responses/skills/`. Use the `download_skill` service to add new skills.
    </Info>

    See [Skills Overview](/skills/overview) for detailed information.
  </Accordion>

  <Accordion title="Functions">
    **Type**: YAML

    **Default**: `execute_services`, `get_attributes`, `load_skill`, `bash`

    Define custom functions that the AI can call. Each function consists of:
    - `spec`: OpenAI function schema defining parameters
    - `function`: Implementation details (type and configuration)

    See [Functions Overview](/functions/overview) for detailed information.

    The Tools page can optionally organize configured functions into **Always available** or **Load when needed** groups without changing their YAML. See [Function Groups](/features/function-groups).
  </Accordion>

  <Accordion title="Context Threshold">
    **Type**: Integer

    **Default**: `40000`

    Maximum provider-reported input tokens before context truncation is triggered.

    <Note>
    The integration uses usage returned by the configured provider. It does not treat Python character length as a token count. A provider that omits usage metadata cannot trigger token-threshold truncation reliably.
    </Note>
  </Accordion>

  <Accordion title="Context Truncate Strategy">
    **Type**: Select

    **Default for new agents**: `keep_recent`

    **Options**: `keep_recent`, `clear`, `summarize`

    Strategy for handling context when the threshold is exceeded.

    - `keep_recent`: Remove the oldest complete user turns until recent context fits. The system prompt and valid function-call/result relationships remain intact.
    - `clear`: Preserve the existing behavior by retaining only the system prompt and latest user turn.
    - `summarize`: Make one bounded model request to summarize older complete turns, then retain that summary and recent raw turns. If summarization fails, the integration falls back to `keep_recent`.

    Summarization never runs recursively. Its provider-reported usage is included in the agent's usage statistics.
  </Accordion>
</AccordionGroup>

## API compatibility

Both API modes use the same Home Assistant conversation and function execution layer. Changing the API mode does not change function definitions, function results, conversation IDs, or Home Assistant service behavior.

Responses mode maps:

- System, user, and assistant history to Responses input messages
- Home Assistant function calls to `function_call` items
- Function results to `function_call_output` items
- Structured outputs to `text.format`
- Reasoning effort to `reasoning.effort`
- Maximum tokens to `max_output_tokens`
- Image attachments to `input_image` and PDF attachments to `input_file`

Streaming remains enabled in both modes. Responses mode also carries encrypted reasoning items between tool rounds. This allows reasoning models to make one or more sequential Home Assistant function calls without losing reasoning context.

## Migration notes

Agents already configured in this renamed fork do not need a migration. A missing API mode behaves as `Auto`, and a missing continue-conversation setting behaves as `HA Default`. Config entries from the original `extended_openai_conversation` integration are intentionally separate and must be configured again if you want equivalent agents in this fork.

Existing memory settings map to the new selector without deleting stored memories: disabled becomes **Off**, enabled with automatic creation disabled becomes **Manual**, and enabled with automatic creation enabled becomes **Automatic**. Existing agents keep their stored context strategy, including the legacy `clear` fallback when no strategy was saved. New agents default to `keep_recent`.

## Usage statistics

Each conversation agent provides disabled-by-default lifetime, today, current-month, and latest-response usage sensors. Provider requests and complete user-turn runs are counted separately, and multi-round tool runs aggregate every model request. Detailed records are content-free and retained separately from indefinite daily/lifetime aggregates. See [Usage statistics](/usage-statistics).

## Test an agent

Open the integration entry under **Settings** > **Devices & services**, select **Configure**, then choose **Test agent**. The test validates local configuration, resolved API mode, Web Search compatibility, memory storage, exposed entity count, and enabled skill count. It makes at most one minimal model request with a no-op function schema and never executes a Home Assistant action.

- Models older than GPT-5.6 continue using Chat Completions in Auto mode.
- GPT-5.4 Mini continues using Chat Completions in Auto mode.
- GPT-5.6 and later GPT-5 models use Responses in Auto mode.
- Select Chat Completions to preserve the old endpoint for any model.
- Select Responses to opt a supported custom model or provider into the new endpoint.

<Info>
**Working Directory**: All file operations and bash commands use `/config/extended_openai_conversation_responses/` as the default working directory. See [File Functions](/functions/read_file) and [Bash Functions](/functions/bash) for details.
</Info>

### Advanced Options

Enable **Advanced Options** in the configuration to access these model-specific parameters. The available options depend on the selected model.

<AccordionGroup>
  <Accordion title="Automatically retrieved memories">
    **Type**: Integer from 0 to 10

    **Default**: `3`

    Maximum relevant user-scoped memories inserted automatically into each request when memory mode is **Manual** or **Automatic**. Set it to `0` for tool-only retrieval.
  </Accordion>

  <Accordion title="Top P">
    **Type**: Number (0-1, step 0.05)

    **Default**: `1`

    **Available for**: Standard models (gpt-4, gpt-4o, etc.)

    Nucleus sampling parameter. Controls diversity via nucleus sampling. Lower values make responses more focused and deterministic.

    <Info>
    Not available for reasoning models (o1, o3, o4, gpt-5).
    </Info>
  </Accordion>

  <Accordion title="Temperature">
    **Type**: Number (0-2, step 0.05)

    **Default**: `0.5`

    **Available for**: Standard models (gpt-4, gpt-4o, etc.)

    Controls randomness in responses:
    - `0.0` - Deterministic, consistent answers
    - `0.5` - Balanced creativity
    - `1.0` - Creative, varied responses
    - `2.0` - Maximum creativity

    <Info>
    Not available for reasoning models (o1, o3, o4, gpt-5).
    </Info>
  </Accordion>

  <Accordion title="Reasoning Effort">
    **Type**: Select

    **Default**: `low`

    **Options**: `low`, `medium`, `high`

    **Available for**: Reasoning models (o1, o3, o4, gpt-5)

    Controls the reasoning depth for reasoning models:
    - `low`: Faster responses, basic reasoning
    - `medium`: Balanced reasoning depth
    - `high`: Deep reasoning, slower responses

    <Note>
    Higher effort increases response time and token usage.
    </Note>
  </Accordion>

  <Accordion title="Service Tier">
    **Type**: Select

    **Default**: `flex`

    **Options**: `auto`, `default`, `flex`, `priority`

    **Available for**: o3, o4, gpt-5 models

    Controls the service tier affecting response latency and throughput:
    - `flex`: Balanced performance and cost
    - `priority`: Faster responses, higher cost
    - `auto`: Automatic selection based on load
    - `default`: Standard tier
  </Accordion>

  <Accordion title="Shorten Tool Call ID">
    **Type**: Boolean

    **Default**: `false`

    Enable to shorten tool call IDs for compatibility with certain providers (e.g., Mistral AI).

    <Warning>
    Only enable if your API provider explicitly requires shortened tool call IDs. Most providers work with standard IDs.
    </Warning>
  </Accordion>
</AccordionGroup>

## Functions Configuration

Functions are defined in YAML format. Here's the default configuration:

```yaml
- spec:
    name: execute_services
    description: Use this function to execute service of devices in Home Assistant.
    parameters:
      type: object
      properties:
        list:
          type: array
          items:
            type: object
            properties:
              domain:
                type: string
                description: The domain of the service
              service:
                type: string
                description: The service to be called
              service_data:
                type: object
                description: The service data object to indicate what to control.
                properties:
                  entity_id:
                    type: string
                    description: The entity_id retrieved from available devices. It must start with domain, followed by dot character.
                required:
                - entity_id
            required:
            - domain
            - service
            - service_data
  function:
    type: native
    name: execute_service
```

<Note>
You can add multiple function definitions to extend the AI's capabilities. See the [Functions](/functions/overview) section for examples.
</Note>

## Skills Configuration

Skills are enabled through a simple multi-select interface:

1. Download skills using the `download_skill` service
2. In Options, select which skills to enable
3. Skills provide context-specific instructions to the AI

Learn more in [Skills Overview](/skills/overview).

## Logging

Monitor API requests and responses by adding this to your `configuration.yaml`:

```yaml
logger:
  logs:
    custom_components.extended_openai_conversation_responses: info
```

This logs:
- Function calls and responses
- OpenAI API interactions
- Skill loading and execution
- Error messages and debugging info
